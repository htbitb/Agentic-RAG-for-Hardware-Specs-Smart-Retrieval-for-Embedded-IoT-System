? What is RAG, and why do we need it?

RAG stands for Retrieval-Augmented Generation. In one sentence:

The one-sentence definition RAG = first retrieve the relevant pages from your documents, then let an AI generate an answer using those pages as its source of truth.

The problem RAG solves

A large language model (LLM) like ChatGPT is brilliant at writing sentences, but on its own it has three big weaknesses:

  • It doesn't know your documents. It was never trained on your ESP32 or FreeRTOS PDFs.
  • It has a knowledge cut-off. It only knows what existed when it was trained.
  • It hallucinates. When unsure, it confidently makes things up — dangerous for technical facts like pin numbers or timing values.
Analogy: closed-book vs open-book exam A plain LLM is a student taking a closed-book exam from memory — fluent, but guessing. RAG turns it into an open-book exam: before answering, the student flips to the exact pages in the manual and answers from what's written there. Same student, far more reliable.

Why this is perfect for ESP32 & FreeRTOS docs

Those manuals are hundreds of pages of dense technical detail. Nobody wants to Ctrl+F through a 700-page PDF. RAG lets you ask "How many cores does the ESP32 have?" in plain English and get an answer grounded in the actual manual, with the page it came from.

Why split it in two? Embedding hundreds of pages is slow and only needs to happen when the documents change. By doing it once and saving the result in a database, every question afterwards is fast.

5 The 5 core elements

Every RAG system is built from these five parts. Here is what each one is, why it's needed, and the specific free tool we chose for it.

1

Data Source the knowledge

What: the raw documents you want answers from. Here: three official PDFs — the ESP32 datasheet, the ESP32 technical reference manual, and the FreeRTOS reference manual, stored in data/pdfs/.

Why: RAG is only as good as its source. Because the answers are built from these files, the assistant is an expert on exactly these topics and nothing else — which is what we want.

2

Embedding Model meaning → numbers

What: a small AI model that reads a piece of text and outputs a list of numbers (a vector) that represents its meaning. We use all-MiniLM-L6-v2, which produces a 384-number vector for any text.

Why: computers can't compare meaning directly, but they can compare numbers. Texts with similar meaning get similar vectors, so "close vectors = related ideas".

Analogy: GPS for meaning An embedding gives every sentence a coordinate in an imaginary "meaning map". "Create a task" and "start a thread" land near each other; "Wi-Fi antenna" lands far away. Searching becomes "find the nearest neighbours on the map".

Why this one: it's free, tiny (~90 MB), runs on a normal laptop CPU with no internet after the first download, and is the industry's classic starter model.

3

Vector Database ChromaDB

What: a database specialised for storing vectors and instantly finding the ones most similar to a query vector. We use ChromaDB, which saves everything to a local folder (chroma_db/) — no server, no account.

Why: we may have thousands of chunks. Comparing your question to every single one by hand would be slow. A vector database is built to do this "nearest-neighbour" search in milliseconds.

Analogy: a librarian who understands ideas A normal database finds books by exact title. A vector database is a librarian who, when you describe an idea, instantly hands you the passages that mean the same thing — even if they use completely different words.
4

The LLM the brain / writer

What: the language model that reads the retrieved chunks plus your question and writes the final, fluent answer. By default we run google/flan-t5-base locally — free and offline.

Why: retrieval alone gives you raw paragraphs. The LLM turns those paragraphs into a direct, readable answer to your specific question.

Why keep the LLM small? A small model runs on any computer with no GPU and no bills. Its answers are basic, but this is a learning project — you can later switch to a stronger model (Ollama's Llama 3) by changing a single line in config.py. That flexibility is the whole point of element 5.
Good to know flan-t5 can only read ~512 tokens (~380 words) at once, so it sees the top couple of chunks. That's fine for learning; bigger models (Ollama) can read much more at once.
5

Orchestration Framework LangChain

What: the "glue" library that connects elements 1–4 into one smooth pipeline. We use LangChain — yes, LangChain and LlamaIndex are the two most popular choices, and we picked LangChain because it's the most widely used and has the clearest separation between the pieces.

Why: without it you'd write a lot of plumbing by hand — loading PDFs, calling the embedding model, talking to Chroma, formatting the prompt, calling the LLM. LangChain provides a ready-made, swappable component for each step, so you focus on ideas, not plumbing.

Analogy: the power strip LangChain is a power strip with standard sockets. Any embedding model, any vector DB, any LLM plugs into the same sockets — so you can swap one out without rewiring everything else.

⚙ The pipeline, step by step

Ingestion — turning PDFs into a searchable index

  1. Load. LangChain's PDF loader reads every page of every PDF into plain text.
  2. Chunk. We slice the text into ~1000-character pieces with 150 characters of overlap.
    Analogy: index cards Imagine tearing a textbook into index cards. Each card is small enough to scan quickly, and the slight overlap means a sentence split across two cards isn't lost.
  3. Embed. The embedding model converts each chunk into a 384-number vector.
  4. Store. ChromaDB saves each vector together with the original text and its source (file name + page number), on disk, so it survives after the program ends.

Querying — answering a question

  1. Embed the question with the same model used during ingestion (crucial — the vectors must be comparable).
  2. Search. Chroma returns the RETRIEVE_K (default 4) chunks whose vectors are closest to the question's vector.
  3. Build the prompt. We paste those chunks into a template that says, in effect: "Answer the question using ONLY this context; if it's not here, say so."
    Why that instruction matters Telling the model to use only the provided context — and to admit when it can't find the answer — is the main trick that stops hallucination.
  4. Generate. The LLM reads the prompt and writes the answer.
  5. Show sources. We also print which file and page each chunk came from, so you can verify the answer yourself.

What it looks like in code (LangChain)

The heart of the query pipeline is just a few lines in rag_core.py. The | symbol means "pipe the output of one step into the next", like a factory line:

prompt = PromptTemplate.from_template(PROMPT_TEMPLATE)
chain  = prompt | llm | StrOutputParser()
answer = chain.invoke({"context": format_docs(docs), "question": question})

Read it as: fill the prompt → send to the LLM → turn the result into a plain string.

🗂 The files in this project

Small on purpose — you can read the whole thing in an afternoon.

config.py

Every setting in one place: which models, chunk sizes, how many chunks to retrieve, which LLM backend. Start here to experiment.

rag_core.py

The engine. Defines the embedding model, the vector store, the LLM, and the answer_question() query pipeline — each mapped to one of the 5 elements.

ingest.py

STEP 1. Runs the ingestion pipeline: PDFs → chunks → embeddings → ChromaDB. Run once.

ask.py

STEP 2. Runs the query pipeline in a loop so you can chat with your documents.

requirements.txt

The list of free libraries to install with pip.

data/pdfs/

Element 1 — the three source PDFs. Drop more PDFs here and re-run ingest.py to expand the knowledge.

▶ How to run it

Full details are in README.md. The short version:

# one-time setup (uses Python 3.9)
& "C:\Program Files\Python39\python.exe" -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# STEP 1: build the index from the PDFs (do this once)
python ingest.py

# STEP 2: ask questions
python ask.py "How many cores does the ESP32 have?"
Tip: see "retrieval" on its own Set LLM_BACKEND = "extractive" in config.py. Now no language model runs — the app just shows the best-matching chunk. It's a great way to see what the retrieval half does before the LLM rewrites it, and it needs zero extra downloads.

📖 Mini-glossary

TermPlain-English meaning
LLMLarge Language Model — an AI that reads and writes text (the "brain").
EmbeddingA list of numbers that captures the meaning of a piece of text.
VectorJust that list of numbers. A coordinate in "meaning space".
ChunkA small slice of a document (here ~1000 characters).
Chunk overlapText shared between neighbouring chunks so ideas aren't cut in half.
Semantic searchSearching by meaning instead of exact keywords.
Top-kThe k most relevant chunks we pull from the database (here k = 4).
ContextThe retrieved chunks we hand to the LLM to answer from.
PromptThe full instruction (context + question + rules) sent to the LLM.
HallucinationWhen an LLM confidently states something false. RAG reduces this.
TokenA chunk of a word the model counts; models have a max token limit.

🚀 Ideas to take it further

  • Better answers: install Ollama, run ollama pull llama3.2, and set LLM_BACKEND = "ollama".
  • More knowledge: drop extra PDFs into data/pdfs/ and run python ingest.py --reset.
  • Tune retrieval: change RETRIEVE_K, CHUNK_SIZE, and CHUNK_OVERLAP in config.py and compare the results.
  • Try another embedding model: swap EMBEDDING_MODEL_NAME for a larger one and see if answers improve.
  • Add a web UI: wrap answer_question() in a small Streamlit or Flask app.
The key takeaway RAG = Retrieval (find the right pages by meaning) + Generation (let an LLM answer from them). Master those two halves and you understand every RAG system, no matter how fancy.
